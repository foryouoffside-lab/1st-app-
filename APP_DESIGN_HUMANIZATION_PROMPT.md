# SkillDrills Pro — App Shell Design Humanization Pass

**Read this whole document before changing anything.** This is a design-only pass on the
app shell that surrounds the drills — navigation, home, daily, progress, auth, category
browsing. It is explicitly **not** a gameplay change and **not** a drill redesign.

## 1. The goal, in one sentence

The app currently looks and feels like it was generated by an AI page-builder (v0/Lovable/
bolt-style output) — competent, consistent, but generic. Make the app-shell screens read
as if a specific person with a point of view designed them for this specific product,
without touching gameplay, scoring, or any drill's mechanics.

## 2. Scope — read this twice, it's the most important section

### IN SCOPE (touch these):
- `app/layout.js`, `app/page.js`, `app/HomePageClient.js`
- `app/loading.js`, `app/error.js`, `app/not-found.js`
- `app/daily/page.js`, `app/daily/DailyClient.js`

- `app/drills/page.js` (the "all drills" browse list — a menu, not a drill)
- `app/drills/cognitive/page.js`, `app/drills/cognitive/CognitiveHubClient.js` (the
  category hub / drill picker — also a menu, not a drill)
- `app/challenge/page.js` and its client (Arena lobby/matchmaking chrome — Arena is
  currently feature-flagged off via `lib/featureFlags.js`, so treat this as low priority,
  do it last if at all)
- `app/privacy/page.js`, `app/terms/page.js` (legal pages — low priority, just bring
  typography/spacing in line with whatever the new system becomes, don't over-invest)
- `components/AppShellClient.js`, `components/MobileHeader.js`, `components/BottomNav.js`
- `components/AuthGate.js` (sign-in / loading / username-setup screens)
- `components/ChallengeNotificationBanner.js`, `components/ChallengeStatusToast.js`,
  `components/CelebrationToast.js` (toast/banner chrome)
- `styles/globals.css` — the shared design tokens and reusable classes. Most of the
  systemic fixes below land here, since it's what every in-scope screen already draws from.

### OUT OF SCOPE — do NOT touch:
- **Every file under `app/drills/cognitive/<category>/<drill-name>/`** — all 25 drills'
  `*Client.js` / `*Client.tsx` gameplay files, and their `page.js` route wrappers. These
  are gameplay, not app design. Do not open them to "improve" anything, even styling —
  a separate pass already standardized their HUD/effects and touching them here risks
  regressing that work.
- **`components/DrillWrapper.js`** — this is gameplay chrome (in-drill header, pause
  modal, result-screen wrapper), not app-shell chrome. Leave it alone even though it's
  a `component/` file.
- **`lib/scoringEngine.js`, `lib/challengeEngine.js`, `lib/canvasFx.js`, `lib/audioSynth.js`**
  and anything else in `lib/` that's game logic, not presentation.
- Anything under `android/` other than icon/splash assets if a rebrand genuinely requires
  it (flag it, don't just change it — regenerating those touches a whole native asset
  pipeline, see `scripts/make-splash.js`).

If you're ever unsure whether a file counts as "a drill," check: does its route look like
`/drills/cognitive/<subcategory>/<name>`, and does it render a `<DrillWrapper>` around an
actual timed game loop? If yes, it's out of scope.

## 3. What's actually wrong (diagnosis, with receipts)

This is a real, working design system — not sloppy, not inconsistent, actually fairly
disciplined (see the CSS custom properties in `styles/globals.css:5-33`: one accent color
per category, a shared `--brand-grad`, real surface/text tokens). The problem isn't a lack
of a system. It's that the specific choices inside that system are the exact ones every
AI page-builder defaults to:

1. **Glow on everything.** `shadow-[0_0_20px_rgba(...)]` / `shadow-[0_0_22px_rgba(...)]`
   style glows sit on nearly every icon badge — the auth logo mark (`AuthGate.js`), the
   category tiles, every drill start-card icon. When everything glows, nothing does.
2. **One universal icon formula.** Every icon in the app — logo, categories, features,
   drills — is "Lucide icon, centered, inside a `rounded-2xl`/`rounded-[14px]` box filled
   with a two-stop gradient." It's applied so consistently it reads as a component
   template rather than a decision made per place.
3. **The violet→indigo→cyan/emerald gradient is the accent for literally everything** —
   auth screen, buttons, badges, category tiles, XP bars. It's not a signature color
   anymore, it's wallpaper. (`--brand-grad` in `globals.css:18` is used almost everywhere
   something needs to look "branded.")
4. **backdrop-blur glass cards over radial-gradient blobs** (`AuthGate.js`'s `Frame`
   component: `backdrop-blur-2xl` panel over a `radial-gradient(ellipse...)` background
   blob) is one of the most recognizable v0/Lovable/bolt signatures there is.
5. **Generic SaaS microcopy.** "Track Progress," "Earn XP & Levels," "Real Google sign-in
   — we never see or store your password," "Loading SkillDrills... Connecting to secure
   servers..." — all correct, all interchangeable with any other app. No voice specific
   to a *drill/training* product.
6. **Perfect symmetry everywhere.** Every card is centered, evenly padded, same corner
   radius family (`rounded-2xl`/`rounded-3xl`). Nothing ever breaks the grid on purpose.
7. **Placeholder-grade gaps that were never finished** — e.g. the Continue Training and
   Daily Challenge cards were rendering raw emoji (`{drill.emoji || '🎯'}`) as icons while
   `.cont-card .ic` in `globals.css` already had a real 24px icon slot sitized and waiting,
   unused. (This specific one is already fixed — mentioned so you know to look for *other*
   half-finished spots like it. If you find one, finish it, don't leave it.)

## 4. The direction to build toward

Don't just strip the above out — replace it with an actual point of view. This is a
**cognitive/reflex training app** ("drills," "Arena," "duels," EIQ ranking). Lean into
that instead of defaulting to generic consumer-SaaS polish. Think **precision instrument /
performance lab**, not **crypto dashboard**:

- **Glow means "live," not "decorative."** A glow should communicate state — a timer
  currently counting down, a streak currently active — never sit permanently on a static
  icon just to look nice. If it's not telling the user something is *happening right now*,
  it doesn't glow.
- **Numbers are the hero, not icon badges.** This is a stats-driven app (scores, streaks,
  levels, accuracy). Let big, confident tabular numerals carry the visual weight on cards
  instead of another icon-in-a-gradient-box. Space Grotesk is already loaded for headings
  (`globals.css:55`) — use it for stat numerals too, not just `<h1>`/`<h2>`.
- **Spend the accent color like a budget, not wallpaper.** Each category already has its
  own color (`--c-cognitive`, `--c-memory`, etc. — `globals.css:24-32`). Use each one only
  where it's identifying *that specific category's own content* (its tiles, its progress
  bars). Reserve the shared `--brand-grad` for exactly one thing app-wide (e.g. the single
  primary "Start" CTA), not for every badge and pill.
- **Give icons a distinct shape language instead of "gradient box."** A drill/reflex app
  can justify a targeting/viewfinder motif — corner brackets (like a camera viewfinder or
  crosshair corners) around key icons or hero elements, instead of a filled rounded square.
  This is achievable in plain CSS/SVG (four short corner-bracket lines), doesn't require
  real illustration skill, and actually ties to what the product does.
- **Let the copy sound like it's written by someone who trains, not a SaaS template.**
  Shorter, more imperative, a little more intense — "Session Log" instead of "Track
  Progress," "Rank Up" instead of "Earn XP & Levels," that kind of register shift. Keep
  it plain-language and honest (no fake urgency, no dark patterns) — just less generic.
- **Break the grid on purpose, once or twice.** Pick one or two moments (the home hero /
  streak area is the obvious candidate) and let it be asymmetric or off-center rather than
  another centered card. Don't do this everywhere — one deliberate break reads as
  intentional; doing it everywhere just becomes a new template.
- **Do not invent a mascot or custom illustration.** That needs a real artist's hand-drawn
  work, and a coding agent generating "custom illustration" in SVG usually looks worse than
  no illustration at all. Skip it — the corner-bracket/typography/color-discipline levers
  above are where the real, achievable wins are.

## 5. Concrete rules to enforce while implementing

- No more than **one** glowing element visible on-screen at a time, and only if it
  represents something currently active/live.
- No more than **one** gradient-filled surface visible on-screen at a time (the primary
  CTA). Everything else uses flat color from the existing token set.
- Every icon needs an explicit reason to sit in a filled box vs. rendered flat/outlined —
  "that's just how we do icons" is not a reason.
- Don't touch the underlying category accent colors (`--c-cognitive` etc.) — those are
  shared with the drill catalog and progress charts; changing them here would create a
  mismatch you can't see from inside this scope.
- Keep `body`/`--ink` dark-mode-only as it is now — there's no light theme in this app,
  don't introduce one.
- Preserve every existing route, prop, and exported function signature unless a change is
  purely cosmetic (className/JSX/CSS). Don't refactor data flow, state, or Firebase calls
  as part of a "design" pass.
- `npx next build` must pass with no new errors before you consider a screen done.
- Keep accessibility where it already exists: `:focus-visible` outline (`globals.css:65-69`),
  reduced-motion handling (`globals.css:71-76`), and don't drop text contrast below what's
  there now chasing a quieter palette.

## 6. Suggested order of work

1. `styles/globals.css` first — most of the systemic fixes (glow discipline, gradient
   discipline, any new shared classes for the corner-bracket icon treatment) belong here
   so every downstream screen inherits them for free.
2. `components/AuthGate.js` — it's the very first screen every signed-out user sees, and
   currently the single most "AI template" screen in the app (the blurred-glass-over-blob
   `Frame`, the generic sign-in copy).
3. `app/HomePageClient.js` + `components/MobileHeader.js` + `components/BottomNav.js` —
   the screen users see most often.
4. `app/daily/DailyClient.js`, `app/progress/ProgressClient.js`, `app/drills/cognitive/CognitiveHubClient.js`.
5. `app/loading.js`, `app/error.js`, `app/not-found.js` — cheap, usually-ignored screens
   that are an easy place to feel bespoke instead of default-Next.js.
6. Toast/banner components, legal pages, Arena — lowest priority, do last if time remains.

## 7. What to report back when done

List every file touched, and for each one: what specifically changed and why (tie it back
to one of the numbered problems in §3 or directions in §4 — not just "updated styling").
This is going to be reviewed against a backup of the pre-change state, so be specific
enough that each change is easy to find and verify in a diff.
